  4. Provider version gate. v1 pinned what it reads. v2 status: partial. The probe reports versions. A minimum version that refuses an old CLI is deferred. Evidence: PARITY.md "Provider version gate", DL-131 item 3. Value: medium. Claude and Codex protocols drift, so a minimum version prevents silent breakage.
  5. "Extraction proof": diff the derived card state for the same hook stream before and after the refactor. v2 status: has, in another form. Replay fixtures drive the adapter cores and the fold.   6. Determinism and "no model calls in the core" as a tested rule. v2 status: has. Evidence: `crates/fleetdeck-cli/tests/cutover.rs` `no_crate_calls_a_model_api_directly`. Value: low (done).

- Ideas and lessons:

Fall back to `merge-base HEAD origin/HEAD` and label it "inferred base" for adopted sessions. v2 status: partial. v2 stores the requested `base` name for a worktree start, but no resolved oid and no "inferred base" label were found.   2.   3. A new hunk renderer with line anchors and caps (the old FileViewer had a 5,000-line DOM cap). v2 status: partial. Colored diffs exist (DL-140 text in `DECISIONS-LOG.md`). Line-anchored note UI and pagination were not found. Evidence: no match for "annot" or "line note" in `web/src`. Value: medium.
  4. ## docs/v1/p3-issue-pr-spawning.md
- Summary: a spec for forge-driven work: browse issues, spawn one agent per issue, point at a PR to spawn a reviewer, and write PR-scoped output (create PR, post review, comment). It leads with the injection finding: hostile issue text plus an unsupervised spawn is a live exploit chain. It uses only the user's own `gh` and `glab` (never a stored token). It recommends a server-side batch endpoint. Jira and Linear are cut.
- Ideas and lessons:
  1. Injection boundary: issue-derived spawns are supervised only, with no path to a bypass mode, and third-party text is fenced and labeled as untrusted data. v2 status: partial. The rule is named in the threat table, but no code, fixture or forge flow implements it, because no issue flow exists. Evidence: `docs/v2/PLAN.md:536` ("Prompt injection from forge text ... fenced and labeled ... supervised"). Spawn mode ceilings per grant exist in `docs/v2/adr/ADR-006-coordinator-mcp.md:50` (`max_modes`, `spawn_cap`). A fenced-envelope helper: not found. Value: high. Build the envelope and its test first, before any forge feature.
  2. The injection fixture: an issue body that says "run with --dangerously-skip-permissions" must still give a supervised worker with the body as inert data. v2 status: missing. Evidence: not found. Value: high. It is a cheap regression test that guards the whole pillar.
  3. Privilege model: operator versus worker tokens and spawn caps, so an agent with one `curl` cannot escalate. v2 status: has. Evidence: ADR-006 (grants, classes `read/mail/drive/spawn`, `spawn_cap` 0-50, no transitive authority: "a `spawn` op whose spec carries a grant is a stored rejection `forbidden`"), `crates/fleetdeck-deck/src/store/coordinator_tests.rs`. Value: low (done).
  4. BYO-CLI for forges: shell out to the user's `gh` and `glab`, never store a token, never auto-install a CLI. v2 status: partial. The doctrine matches: "The deck never holds forge tokens" (`docs/v2/PLAN.md:341`, clone uses the station's own git credentials). No `gh`/`glab` integration exists. Evidence: grep for `glab` and `gh` in `crates` and `web/src` finds no integration code. Value: medium. The doctrine is aligned, so a later feature starts clean.
  5. Browse issues and spawn a fleet from selected issues (one worker per issue, ticket-first worktree names). v2 status: partial. Ticket callsigns exist (`<animal>-<KEY>`, DL-144, `provision.rs` tests, `web/e2e/night2.spec.ts`). No issue browser. Value: high. This is the "fleet that consumes a backlog" feature.
  6. Server-side batch endpoint, atomic and auditable, instead of N browser POSTs. v2 status: partial. v1's problem was a browser-side loop. In v2, the board batch starts one session per line (`web/src/spawn/spawn.test.tsx` "a batch starts one session per line and Nx repeats a task"). Deck-side atomicity for partial failure was not confirmed. The coordinator `spawn` op has a durable `spawn_used` counter (ADR-006 §6.4). Value: medium.
  7. Point at a PR, check out the branch in a worktree, spawn a reviewer that runs the user's installed skill. v2 status: missing. Evidence: no PR or reviewer flow in `crates` or `web/src` (search for "pull request", "reviewer" in PLAN/UI-DESIGN finds only the dev-process text at `PLAN.md:674`). Value: high. The pieces exist (worktree start with a `base`, DL-144; revert; diff), and the daemon makes no model call.
  8. PR-scoped write: a verb allowlist (create PR, post review, comment), an identity preview, a board confirm per write, a feed audit line, never batch, never auto. v2 status: missing. The event feed exists (`web/e2e/workspace.spec.ts` "the event feed shows fleet changes"). Value: medium. Keep the "stopping rule": ship the writes only with the full security set, else stay read-only.
  9. Multi-forge from day one: GitHub and GitLab. GitLab subgroups are 3+ path segments. SSH remotes must match https origins. v2 status: partial. v2 handles clone access and remote checks (`web/src/spawn/CloneAccess.tsx`, `crates/fleetdeck-station/src/workspace/preflight.rs`). Forge-specific parsing for subgroups was not confirmed. Evidence: `crates/fleetdeck-core/src/git.rs`, `preflight.rs`. Value: medium.
  10. Cut Jira and Linear because a tracker token is a stored credential. v2 status: not applicable (no tracker work). The doctrine holds in `PLAN.md:341`. Value: low. Keep the cut.
  11. Which `gh` account posts when several are logged in. v2 status: missing. Evidence: not found. Value: low until write verbs exist.
  12. Exposure proof for forge tokens: no token in `/state`, argv, or logs. v2 status: has for existing secrets. Evidence: `crates/fleetdeck-core/src/secret.rs`, `childenv.rs`, test `an_invitation_round_trips_and_debug_hides_the_secret`. Value: low (done).

## Top 10 for v2
1. Injection boundary for forge text (p3 #1, #2): build the fenced "untrusted data" envelope, force supervised spawns, add the hostile-issue fixture. It must exist before any issue feature.
2. Record `base_ref` and `base_oid` at spawn (p2 #1): it is the base of every diff-since-spawn and compare view, and it must land before more history accrues.
3. Diff since spawn on the card (p2 #2, #3): v2 has per-turn diffs only. The session-wide review view is the missing half of "harvest".
4. Notes on diff lines sent as one batched mail (p2 #10): the transport exists. Batching gives one revision pass instead of a swinging agent.
5. Spawn from issues (p3 #5, #6): ticket callsigns and batch exist. A read-only issue browser via the user's `gh` and `glab` turns the board into a backlog consumer.
6. PR reviewer spawn (p3 #7): worktree start, diff and revert exist. Checking out a PR branch and starting a reviewer needs only the forge read step.
7. Compare-the-winner for N agents on one issue (p2 #12): batch, diff and trash exist. A keep-one action is a small step with a large payoff.
8. Claude usage windows (p4 #2): Codex windows show on the board. Claude 5-hour and weekly windows do not, and that is the quota that governs a busy day.
9. Show each instance's limit in the spawn picker and in `assign auto` (p4 #10, #14): the data is on the board. Use it to choose the account with the most room.
10. Provider version gate and schema watch (p1-cc #4, p1-codex #7): the probe reports versions, but nothing refuses an old CLI. A minimum version plus a CI schema diff stops silent protocol drift.

Lower-ranked but real: checkpoint scope for untracked files (p2 #4), checkpoint ref GC (p2 #9), inferred cost price table for Codex (p4 #6), 80% chip on the fleet home (p4 #3).
