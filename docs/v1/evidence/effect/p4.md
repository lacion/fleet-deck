## Root cutover and ownership

- [`fleetd.ts`](../../../../src/daemon/fleetd.ts) is only the Bun shebang, imports, and one
  `BunRuntime.runMain(DaemonApp, ...)` call. Production TypeScript contains exactly one
  `BunRuntime.runMain`, no `ManagedRuntime`, and no P3 bootstrap-runtime module or construction
  path.
- [`root-program.ts`](../../../../src/daemon/app/root-program.ts) constructs one cold root Layer,
  installs the host signal observer before aggregate acquisition, keeps the application alive with
  `Effect.never`, and runs policy close from an `onExit` inside the provided Layer. BunRuntime's
  automatic failure reporter is disabled; the owning interpreter preserves one-line startup
  messages and reports defects once.
- [`live-layer.ts`](../../../../src/daemon/app/live-layer.ts) composes AppConfig, ProcessRunner,
  ProcessRuntimeControl, one captured-context IngressSupervisor, and the aggregate daemon
  lifecycle. The remaining compatibility `execFileP` Promise facade submits through this root
  supervisor; it cannot create a second runtime or rebuild the Live Layer.
- The only production callback crossings are the three context-bound runner constructors in
  [`ingress-supervisor-live.ts`](../../../../src/daemon/platform/bun/ingress-supervisor-live.ts).
  Quiesce refuses new submissions and closing joins/interrupts admitted work before store
  retirement.
- [`LifecycleCoordinator`](../../../../src/daemon/app/lifecycle-coordinator.ts) executes the exact
  eight §6 phases once: quiescing, stopping producers, withdrawing discovery, releasing holds,
  closing clients, closing HTTP, closing store, and releasing process ownership. A single monotonic
  absolute budget is shared across every phase; force accelerates an owner but never substitutes
  for its join obligation.
- [`DaemonHostControl`](../../../../src/daemon/app/host-control.ts) leaves the stock runner in
  charge of first-signal root interruption. A concurrent second signal synchronously opens the
  same coordinator's one-way force latch; it never starts an Effect or finalizer from the signal
  callback. Custom teardown maps safe signal cleanup to exit 0 and any deadline, phase, resource,
  or process-release failure to exit 1.

The P3 `BootstrapRuntimeBridge` and P4 root are therefore never live together. No new detached-work
allowlist entry was introduced. Process groups remain the P3 registered detachment policy; the
bounded acquisition finalizer retains and observes a late-retirement continuation so a late
successful acquisition is closed exactly once rather than abandoned.

## Deadline and force policy

P4 records one **1,750 ms** whole-daemon deadline. The ordinary takeover helper waits 2,000 ms and
managed stop paths use 3,000 ms, so a clean root has 250 ms of external publication margin before
the shortest incumbent-death observer expires. The coordinator and acquisition finalizer reserve
their last **250 ms** for synchronous force actions.

Ordinary subprocess timeout/abort still grants the established one-second TERM grace. Root
shutdown is different by design: deadline reserve or a second signal synchronously force-closes
the shared Bun process driver, terminal controls, and native HTTP/client owners; TERM-resistant
admitted commands may therefore go directly to KILL within the remaining root budget. The real
process measurement below proves that policy and reaping behavior.

The existing discovery stop watchdog remains a separate **1,000 ms** sub-deadline. It is neither
added to nor awaited after the root budget. The measured mDNS case uses one first signal and a
200 ms send callback, observes exactly one TTL-0 goodbye and its one callback, then proves exit and
network cleanup under the separate watchdog.

One safety refinement differs from a literal reading of the phase label in the plan: the
`releasing-process` phase retires process callbacks, but verified pidfile deletion is retained
through all idempotent Layer fallbacks and executed synchronously by custom host teardown
immediately before process exit. Removing the pidfile earlier would let a successor claim HOME
while a Layer finalizer could still touch SQLite or other daemon state. Tests assert that this host
release is the final observable action on healthy, failure, acquisition, and hard-deadline paths.

## Acquisition, exit, and active-resource proofs

The production acquisition seam has ten post-ownership checkpoints: pid claim, durable config,
process runtime, database, core, HTTP owner, background owners, listener, discovery/network, and
pollers/boot. The focused matrix injects both failure and interruption after every checkpoint and
asserts the exact acquired prefix and reverse dependency-safe release list. It additionally covers
the uninterruptible process-driver attachment boundary and a real bind conflict.

| Path | Required and observed result |
| --- | --- |
| Successful root / finite root | Exit 0; one cleanup; signal listeners and root keep-alive removed |
| Typed startup refusal | Exact one-line stderr; exit 1; acquired prefix retired |
| Native bind conflict | Exact established message; exit 3; pid, listener, facade, ingress, and owners retired |
| Root defect | Reported once; exit 1; finalizers still run |
| Signal during each acquisition checkpoint | Interruption-only Cause; exact prefix joined; exit 0 |
| Failure after each acquisition checkpoint | `DaemonStartupError`; exact prefix joined; exit 1 |
| First and repeated signals in every active shutdown phase | One close run and one synchronous force transition; no duplicate finalizer |
| Stuck phase / hard deadline | Force once; unsafe store close skipped; host fallback last; exit 1 under the bound |
| Held HTTP hook and active board WebSocket | Canonical `200 {}` before transport close; viewer retires; one mDNS goodbye |
| TERM-resistant admitted command | Second signal force-KILLs and reaps it before daemon exit |

The acquisition fixtures inspect the child before process exit and observe no remaining child,
process, TCP, UDP, timer, timeout, or root keep-alive resource, plus zero SIGINT, SIGTERM, and
unhandled-rejection listener deltas. The external measurement then checks the exact daemon and
known child PIDs, owned pidfile, listener rebind, socket/fd lifetime, scheduled-callback lifetime,
and root-process lifetime after every run and repeats the observation 50 ms later.

## Remaining transition and rollback state

P4 intentionally retains two migrations owned by later packages:

1. `TransitionalAppConfig` preserves the old preflight authority until P5 moves boot/config into
   application services.
2. The temporary `execFileP` compatibility facade is now root-supervised but remains until its
   callers migrate and P13 deletes the facade.

No public wire or database schema changed, so the architectural rollback remains the plan's
complete switch back to the P1/P3 plain `DaemonResources.close()` plus bootstrap-process owner—
never a partial bypass of P4 finalizers. The P4 implementation checkpoint is `661dfe3`. Its parent
`bcf3337` is the proven P3 anchor and the complete rollback target; rollback must restore the P3
bootstrap owner and plain P1 resource close together, never bypass only part of the P4 finalizer
graph.
