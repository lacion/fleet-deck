# S-EVENTS: what do Claude and Codex do with MCP events? (MCP P2)

- **Date:** 2026-10-20
- **Versions:** Claude Code 2.1.302 (`claude`, model `claude-haiku-5-5`), Codex 0.163.0 (`codex app-server`, default model `gpt-daybreak-blue-latest`, `model_reasoning_effort="low"`), `rmcp` 3.5.1 (pinned `=3.5.1`), rustc 1.96.0, edition 2024.
- **Result:** **PASS with notes.** Every experiment of the brief ran once; five extra runs were added (C4B, C4C, C4D, X2B, X3B, see 4.2). Result in one paragraph: a running Claude session learns a new tool without a restart, through a `subscriptions/listen` stream and `notifications/tools/list_changed` (C1); it does not poll by `ttlMs` (C2). A running Codex 0.163.0 session never learns a new tool, with or without a GET stream, with or without `mcp_2026_07_28` (X1A, X1B, X1C). No host subscribes to a resource (C3, X1). Both hosts send a `progressToken`, but neither host shows the progress in its output, and progress does not keep a call alive (C4D, X2B). Claude cancels a call by closing the HTTP request stream (C5). Codex does **not** cancel anything at the server on `turn/interrupt` or on a tool timeout (X3, X3B, X2B): the server work runs until the Codex process ends.

## 1. Question

Fleet Deck runs Claude as `claude -p --input-format stream-json ...` and Codex as `codex app-server`, with MCP over HTTP. Our station serves `rmcp` stateless (`with_legacy_session_mode(false)`, `with_json_response(true)`). What do the two hosts do with MCP events from such a server: list changes, resource updates, progress, cancellation and cache TTLs?

## 2. Method

- `spikes/s-events/` is a standalone crate (own `[workspace]` and `Cargo.lock`, `/target/` ignored). `src/main.rs` builds the HTTP server `events-server` with `rmcp` 3.5.1 (`server`, `macros`, `schemars`, `transport-streamable-http-server`) on `127.0.0.1:<port>` (port 0: chosen by the OS, printed as `PORT=<n>`). Flags: `--stateless` (default; `with_legacy_session_mode(false)`, `NeverSessionManager`) or `--stateful` (`with_legacy_session_mode(true)`, `LocalSessionManager`); `--json` (default) or `--sse` (`with_json_response` on or off); `--no-listen` (`accepted_subscription_filter` returns `None`).
- It serves:
  - tool `slow_count { seconds }` (at most 120): counts one second at a time, sends `notifications/progress` each second when the request has a progress token, stops on `ctx.ct`, returns `done:<n>`;
  - tool `tick`: returns `tick`; after the first call it enables the tool `late_tool` (returns `LATE-OK`) and, 300 ms later, emits `notifications/tools/list_changed` on every open listen stream and on every legacy session peer (the GET stream);
  - resource `fleet://board` (`text/plain`, text `The board word is BOARD-<n>.`). `touch $EVENTS_DIR/bump` (polled every 200 ms) increments `<n>` and emits `notifications/resources/updated` on the listen streams that accepted the URI and on the legacy peers that called `resources/subscribe`;
  - `tools/list` and `resources/list` with `ttlMs` 5000 and `cacheScope` `private` for a modern request (the 2026-07-28 era);
  - capabilities: tools (`listChanged`), resources (`listChanged`, `subscribe`).
- The log (`$EVENTS_LOG` and stderr) has: every HTTP request (method, path, JSON-RPC method and id, `Mcp-Method`, `MCP-Protocol-Version`, `Mcp-Session-Id`, `Accept`, protocol version, progress token, `_meta` keys), the status and content type of each response, every frame that the server writes (`wire frame`), every notification that the handler sends, the opening and the closing of every listen stream with its filter, `notifications/cancelled` (an `on_cancelled` handler), `ctx.ct` cancelled in `slow_count`, and a line when a response body **ends** (the server ended it) or is **dropped** (the client closed the HTTP stream).
- **Deviations from the brief:** two flags were added that the brief does not name: `--no-listen` (the brief names the behaviour for C2) and the environment variable `EVENTS_NO_PROGRESS` (a control run, C4C). The log has the extra `wire frame` lines.
- `run.sh` starts one `events-server` per experiment, in a new temporary directory, and runs the host driver there with a 300 s bound. `claude_session.py` drives `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --permission-mode dontAsk --model claude-haiku-5-5 --no-session-persistence --strict-mcp-config --mcp-config <events, type http> --allowedTools mcp__events ListMcpResourcesTool ReadMcpResourceTool` (a multi-turn session over stdin; the interrupt is the `control_request` `interrupt` of `crates/fleetdeck-providers/src/claude/control.rs`). `codex_events.py` drives `codex app-server -c model_reasoning_effort="low" -c mcp_servers.events.url=... -c mcp_servers.events.default_tools_approval_mode="approve"` (JSON-RPC over stdio: `thread/start` with `approvalPolicy` `never` and `sandbox` `read-only`, `turn/start`, `turn/interrupt`). The outputs stay in the temporary directory and are not in the repository.
- Differences from Fleet Deck: Claude runs with `--permission-mode dontAsk` and without `--permission-prompt-tool stdio`; Claude runs with `--strict-mcp-config` (only the `events` server); Codex also loads the user's own MCP servers (`codegraph`, `codex_apps`). The spike wrote no file of its own into `~/.claude` or `~/.codex` (the CLIs keep their own state there).
- Models and a time stamp differ between runs; every row is one run. The evidence is the server log and the host timeline, not the model answer alone.

## 3. Reproduce

```sh
umask 022 && sh tools/heavy.sh cargo build --manifest-path spikes/s-events/Cargo.toml
sh spikes/s-events/run.sh              # all experiments, one run each
sh spikes/s-events/run.sh C1 X3        # chosen experiments
```

`run.sh` needs `jq`, `python3`, `timeout` and both CLIs signed in. It starts real model runs. The server log of each run is `<tmp>/<id>/events.log`; the host timeline is `<tmp>/<id>/timeline.txt`.

## 5. Answers

**(a) Can a running session learn a new tool without a restart, and by which mechanism?**
- **Claude: yes.** Mechanism: `subscriptions/listen` stream (the client opens it after `server/discover`, asking `toolsListChanged` and `resourcesListChanged`), `notifications/tools/list_changed` on it, and a new `tools/list` 7 ms later (C1). The next turn has the new tool in its tool list and the model can call it. Without a listen stream (C2) the tool did not appear in 13 s or more: the TTL (`ttlMs` 5000) is **not** used to refetch.
- **Codex 0.163.0: no.** Codex does not re-list after `list_changed`, also when it has a GET stream (X1B: it got the notification and did nothing) and with `mcp_2026_07_28` (X1C: it does not open `subscriptions/listen`). A tool that appears after the start is visible only to a new Codex session. (The tool list of `mcpServerStatus/list` does show it, because that call connects again.)

**(b) Does any host act on `resources/updated`?**
No. Claude asks only `toolsListChanged` and `resourcesListChanged` in the listen filter and never sends `resources/subscribe` (C3: the server's sink refused the update because no URI was accepted). Codex never sent `resources/subscribe` (X1A, X1B, X1C). Both hosts read a resource only when the model calls the resource tool. Not measured: a server that sends `notifications/resources/list_changed` (Claude asked for it in the filter), and a listen filter with `resourceSubscriptions` (no host sent one).

**(c) Do progress notifications reach the host, and do they keep a long call alive?**
- They reach the host process: both hosts send a `progressToken` in `tools/call` (Claude: the JSON-RPC id; Codex: its own counter) and the server stream carries the progress frames (C4: 90 frames).
- They do **not** show up in the host output: the Claude stream-json output has no progress text (only Claude's own `tool_progress` heartbeat every 30 s); the Codex app-server sent no `item/mcpToolCall/progress` (X2).
- They do **not** keep a call alive: with a 10 s limit the call timed out at 10 s with a progress notification each second, on both hosts (C4D, X2B). Claude's per-server `timeout` key is a hard limit. Claude's `MCP_TOOL_TIMEOUT` env var had no effect at all in this mode (C4B, C4C). Long calls succeeded by default on both hosts: Claude 90 s (C4), Codex 90 s (X2); the default limits were not measured (Codex's must be above 90 s).

**(d) How does cancellation reach the server?**
- **Claude:** by closing the HTTP request stream of the `tools/call` POST, at once after an `interrupt` control request (C5, same 0.1 s) and after a timeout (C4D). rmcp turns the close into `ctx.ct` cancelled. No `notifications/cancelled` was sent. The server must read `ctx.ct`.
- **Codex:** not at all in 0.163.0. `turn/interrupt` ends the turn in the host (`interrupted`) and a tool timeout fails the item, but the HTTP stream stays open and no `notifications/cancelled` is sent (X3, X3B, X2B). The server sees the close only when the Codex process ends (or the connection drops). A tool that runs long needs its own limit on the server side.

**(e) What does each host need from the server (stateless or stateful, JSON or SSE)?**
- **Claude:** the 2026-07-28 era (`server/discover`) works with `--stateless`, both `--json` and `--sse`. `subscriptions/listen` and progress are served as `text/event-stream` also with `json_response` on: rmcp leaves JSON mode when the handler sends a notification (C4 shows `listen:0` accepted and the `tools/call` stream with progress, both with `--json`). So the station configuration (`with_legacy_session_mode(false)`, `with_json_response(true)`) already supports (a) and (d) for Claude, if the handler implements `accepted_subscription_filter` and `listen` and reads `ctx.ct`. A server that answers the listen request with an error (C2: HTTP 404) makes Claude retry 3 times and then work without events.
- **Codex:** legacy era (`initialize` `2025-06-18`). `--stateless` gives no standalone stream (`GET /mcp` answers 405 and Codex works on); `--stateful` gives a GET stream and a `Mcp-Session-Id`, but nothing in (a) to (d) improves for Codex (X1B, X3 are by design of the host). With `mcp_2026_07_28` Codex speaks the modern era and is as passive as in the legacy era (X1C). The server mode is therefore not a lever for Codex in 0.163.0. A stateless station gets the same Codex behaviour as a stateful one.

## 6. Limits of this spike

- One run per experiment (and the extra runs of 4.2), one model per host. The model's text can vary; the tool calls, the server log and the host timeline are the evidence.
- The X1A run used the first form of the driver (see the X1A row); X1B and X1C used the final one. The extra runs C4B, C4C, C4D, X2B, X3B were added to answer (c) and (d) because the default 90 s run cannot show a timeout or a cancel; they are listed in `run.sh`.
- The Claude `MCP_TOOL_TIMEOUT` result (C4B, C4C) is a negative result without a cause. The Claude default tool timeout was not measured, and the exact Codex default `tool_timeout_sec` was not read (it is above 90 s). Codex was not run with `mcp_2026_07_28` against `--stateless`.
- Not measured: `resources/list_changed`, `resourceSubscriptions` in a listen filter, `prompts/*` events, Claude against a legacy-era stateful server (Claude opened with `server/discover` in every run), Claude `ttlMs` of a value above the session length, many listen streams in one process (the `listen` handler of the server keeps every stream open until the client closes it), and Fleet Deck's own permission prompt tool, which the harness replaced with `--permission-mode dontAsk`.
- Claude exited with code 1 in C5 because the interrupt gives an error `result`; this is the normal result of an interrupt and not a failure of the run.
